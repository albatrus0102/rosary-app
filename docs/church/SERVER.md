# 사이버 성당 서버 운영 안내 (S-01 용량·샤딩)

대상 독자: 소유자와 운영 담당. 구현은 `server/church/`, 프로토콜 원문은 `docs/church/SPEC.md`(§8~16)입니다.
배경: 한국 온라인 성당 '산사'가 입소문이 나서 첫날 서버가 죽었습니다(동시 20명). 홍보 전에 성당 서버가 **2000명 이상**을 **누구도 돌려보내지 않고** 받아야 합니다(소유자 규칙: 이용 제한 없음, SPEC §15).

## 1. 구조 한눈에

```
앱 ──ws──> Worker(index.ts) ──assign()──> ChurchDirectory(성당당 1개 DO)
                │                             ▲  report()  (방이 인원·기도·초 수를 보고)
                └──────── fetch ──> ChurchRoom(방 DO: basic-1, basic-2, ...)
```

- **ChurchRoom**: 방 하나. 같은 방 사람끼리만 아바타로 서로 보입니다(기존 로직 그대로).
- **ChurchDirectory**(새로 추가): 성당마다 하나. 방 번호별 인원을 알고 있다가 새 접속자가 올 때 "어느 방으로 갈지"를 정해 줍니다. Durable Object 끼리는 서로를 목록으로 볼 수 없어서 필요한 중간 장부입니다.
- 사용자에게는 샤딩이 보이지 않습니다. 같은 성당의 다른 방 사람이 안 보일 뿐이고, 인원수(`n`)·"지금 N명 기도 중"·"오늘 켜진 초"는 모든 방의 합계입니다.

## 2. 방 배정 정책 (코드: `src/directory_logic.ts`)

| 항목 | 값 | 이유 |
|---|---|---|
| 방 정원 목표 `ROOM_TARGET` | 60명 | 과부하 단계 0(전송 200ms, 반경 40m, 80명 가시)이 유지되는 최대 인원. 렌더링 비용 기준(클라이언트는 가까운 80명까지 그림)보다 여유 |
| 배정 | 목표 미만인 방 중 **가장 찬 방** | 방이 한산하게 흩어지지 않고 북적이게(빈 방 대책, C-05). 같으면 번호가 작은 방 |
| 넘칠 때 | 아직 안 쓴 가장 작은 번호의 새 방을 연다 | 거절 없음 |
| 방 번호 한도 | 1..50 (SPEC §9) → 성당당 3000명까지 단계 0 | 50개가 모두 60 이상이면 가장 한산한 방에 넣는다. **그래도 거절하지 않는다** |
| 방이 죽었을 때 | 20초(`ROOM_TTL_MS`) 보고가 없으면 0명으로 본다 | 방은 접속자가 있으면 5초마다, 변화가 있으면 1초 안에 보고하고 비면 즉시 0을 보고 |
| 동시에 몰릴 때 | 배정마다 '미확정 1명'을 더한다(15초 만료, 방이 접속을 받았다고 보고하면 제거) | 방이 보고하기 전에 수백 명이 몰려도 정원 목표가 지켜진다(테스트: 2000명 연속 배정 → 34개 방, 방당 ≤ 60) |
| 디렉터리 장애 | 1.5초 안에 응답이 없으면 `<성당>-1..4` 중 임의 방으로 보낸다 | 입장을 막지 않는다 |
| 빈 성당 | 항상 `<성당>-1` | 촛불이 저장된 방으로 모인다 |

"앉은 사람이 많은 방 우선"은 넣지 않았습니다(가장 찬 방 우선으로 충분히 비슷하게 동작하고, 앉은 사람 수는 방이 1초 단위로만 보고하므로 정확도가 낮습니다).

**알려진 한계**
- 방별 촛불 저장소가 따로라 같은 성당이라도 방이 다르면 켜진 촛불 모양이 다릅니다. "오늘 켜진 초" 숫자는 합산됩니다.
- 사람이 빠져 방이 줄어도 사람을 옮기지는 않습니다(접속 중인 사람은 방이 바뀌지 않음). 새로 오는 사람이 가장 찬 방으로 가므로 한산한 방은 자연스럽게 비워집니다. 재접속하면 새로 배정됩니다.

## 3. 프로토콜 변경(모두 추가형, 기존 앱 그대로 동작)

- 접속: 기존 `GET /ws?room=<성당>-<N>&v=1` 은 N 을 무시하고 서버가 방을 배정합니다. 앱은 `welcome.room` 을 `_room` 에 저장해 재접속 때 그 이름을 다시 보내므로, 재접속은 새로 배정됩니다. 새 형식 `?church=<성당>`(`v` 생략 가능, `client=<id>` 등 모르는 파라미터는 무시)도 받습니다. `&pin=1` 은 방 직접 지정(스모크·디버그 전용).
- 배정된 방 이름: `welcome.room` 과 업그레이드 응답 헤더 `x-church-room`.
- **`n` 의 뜻이 '이 방 인원'에서 '성당 전체 인원'으로 바뀝니다**(SPEC 이 원래 "전체 인원수"라고 정의). `welcome/join/leave/snap` 의 `n` 이 모두 합계입니다. 다른 방 인원은 최대 약 5초 늦게 반영됩니다.
- `welcome.presence` = `{n, seated, praying, candlesToday}` (추가 필드; 구 앱은 무시).
- 새 서버 메시지 `{"t":"presence","n":..,"seated":..,"praying":..,"candlesToday":..}`: 값이 바뀌었을 때 최소 10초 간격, 같아도 60초마다 모든 접속자에게. 구 앱은 알 수 없는 `t` 를 무시합니다(`church_protocol.dart` 확인).
- `GET /stats` (CORS `*`, Worker 안 5초 캐시):

```json
{"ok":true,"at":1794483238256,"tz":"Asia/Seoul","day":"2026-11-12",
 "total":{"live":200,"seated":12,"praying":9,"candlesToday":20,"rooms":4},
 "churches":{"basic":{"live":200,"seated":12,"praying":9,"candlesToday":20,"rooms":4}, "...":{}}}
```

  `live` = hello 를 마친 접속자 합계(방이 20초 안에 보고한 것만). `praying` = 앉아서 기도 중, `seated` = 앉은 사람(기도 중 포함). `candlesToday` = 오늘(한국 시간 00:00 이후) **실제로 켠 횟수**의 합. 방마다 `lit` 카운터를 저장소에 두고 켤 때마다 올립니다(촛불 행은 같은 슬롯 교체 때 덮어써지므로 행 개수가 아니라 켠 횟수를 셉니다). 가짜 값은 없고, 서버 변경 이전에 켠 초는 센 기록이 없어 0으로 나옵니다.
  앱이 `/stats` 를 자주 부르지 않게 하세요: 접속 중에는 `presence` 메시지로 같은 숫자를 받고, 성당 선택 화면에서만 가끔(예: 30~60초에 한 번) 부르는 것을 권합니다. 호출 한 번이 성당 수(현재 8) 만큼의 디렉터리 요청이 됩니다.

## 4. 과부하 단계 (코드: `src/room_logic.ts`, 순수 함수 + 단위 테스트)

| 단계 | 올라가는 조건(둘 중 하나) | snap 간격 | AOI 반경(이탈) | 가시 아바타 상한 |
|---|---|---|---|---|
| 0 보통 | – | 200ms | 40m (44) | 80명 |
| 1 바쁨 | 방 인원 > 60 또는 초당 수신 > 500 | 400ms | 28m (31) | 50명 |
| 2 매우 바쁨 | 방 인원 > 120 또는 초당 수신 > 1000 | 800ms | 20m (22) | 30명 |

- 올라갈 땐 즉시, 내려올 땐 문턱의 85%(속도는 85%)보다 낮아져야 내려옵니다(`nextLoadLevel`, 상수 `LOAD_LEVELS`, `LOAD_UP_PEERS`, `LOAD_UP_RATE`, `LOAD_DOWN_FACTOR`).
- 줄어든 반경 밖이거나 상한 밖인 피어는 `leave{aoi:true}` 로 알립니다(앱은 기록만 두고 숨김). 사용자에게 보이는 안내·거절은 없습니다. `n` 은 단계와 무관하게 정확합니다.
- 단계가 있는 동안 2초마다(인원이 많으면 인원×10ms) 가시 집합을 가까운 순으로 다시 정렬합니다.
- 방 정원 목표가 60이라 샤딩이 정상이면 단계 0 에 머뭅니다. 단계 1~2 는 (a) 50개 방이 모두 찬 뒤 넘치는 경우, (b) 메시지가 비정상적으로 많은 경우의 안전장치입니다.

## 5. 부하 테스트

로컬(권장 시작점):

```bash
cd server/church
npm ci
npm test                                   # 단위 테스트
npm run dev                                # 터미널 1: wrangler dev (http://127.0.0.1:8787)
npm run smoke                              # 터미널 2: 기능 확인(PASS/FAIL)
npm run loadtest -- --bots 500 --ramp 50 --duration 30
npm run loadtest:dry -- --bots 2000 --ramp 100        # 네트워크 없이 CI 용 (가상 시계, 몇 초)
npm run loadtest:dry -- --bots 2000 --single          # 샤딩을 끄면 과부하 단계가 어떻게 동작하는지 관찰
```

- `loadtest.mjs` 는 봇이 걷고(2.5m/s, 5Hz), 가끔 앉아 기도하고, 이모트와 촛불을 하며, 연결 시간·hello→welcome·ping→pong 왕복(DO 로직 경로를 지나는 `{"t":"ping","k":1}`)·끊김·방 분포를 요약표로 출력하고 `/stats` 를 읽어 대조합니다. 램프업 기본 25명/초. **로컬이 아닌 주소에는 `--allow-remote` 를 붙여야만** 실행됩니다.
- **홍보 전 시험은 운영 Worker 가 아니라 별도 시험용 배포에서 하세요**: `npx wrangler deploy --name rosary-church-staging`(저장소·DO 가 분리됨). 봇이 켠 촛불이 운영 "오늘 켜진 초"에 섞이면 안 됩니다(가짜 숫자 금지). 시험 후 시험용 Worker 는 지웁니다(`npx wrangler delete --name rosary-church-staging`). 로컬 시험 뒤에는 `server/church/.wrangler/state` 를 지웁니다.
- 부하를 거는 PC 가 병목이 되지 않게 봇 2000개는 성능이 좋은 PC 에서 `--ramp 100` 이하로, 필요하면 두 대로 나눠 실행하세요(각각 1000). `ulimit -n` 이 4000 이상이어야 합니다.
- 통과 기준(제안): 전원 welcome, 연결 실패·끊김 0, ping→pong p95 < 300ms(같은 지역), `/stats` 의 live 가 봇 수와 일치.

## 6. 배포 (소유자가 할 일)

에이전트는 배포하지 않습니다. 소유자 준비물:

1. **Cloudflare 계정과 API 토큰**(권한: Workers Scripts 편집, Account 읽기). 토큰은 채팅에 붙여넣지 말고 에이전트가 띄우는 **보안 자격증명 입력 폼**(`request_credential`, 호스트 `api.cloudflare.com`)으로만 입력합니다.
2. 네트워크 허용 호스트: `api.cloudflare.com`(wrangler 배포), 배포 후 확인용 `rosary-church.<계정-서브도메인>.workers.dev`(`curl`, 스모크, 부하 테스트).
3. 유료 플랜: 무료 플랜의 일일 요청 한도(확인 필요, 문서 기준 10만 건/일 수준)는 홍보 첫날 금방 넘습니다. 홍보 전에 Workers Paid 로 올리는 것을 권합니다(요금·한도는 소유자가 Cloudflare 공식 페이지에서 직접 확인).

```bash
cd server/church
node ../../tools/church_web/export_layouts.mjs     # 레이아웃을 최신으로
npm ci && npm test && npm run typecheck
export CLOUDFLARE_API_TOKEN=...                    # 폼으로 받은 토큰(코드/채팅에 남기지 말 것)
npx wrangler deploy --name rosary-church-staging   # 1) 시험용으로 먼저 배포하고 부하 테스트
npx wrangler deploy                                # 2) 이상 없으면 운영 배포
curl https://rosary-church.<서브도메인>.workers.dev/health
curl https://rosary-church.<서브도메인>.workers.dev/stats
```

`wrangler.toml` 은 이미 다음을 담고 있습니다.

```toml
[[durable_objects.bindings]]
name = "CHURCH_ROOM"        class_name = "ChurchRoom"
[[durable_objects.bindings]]
name = "CHURCH_DIRECTORY"   class_name = "ChurchDirectory"      # 새로 추가
[[migrations]]  tag = "v1"  new_sqlite_classes = ["ChurchRoom"]
[[migrations]]  tag = "v2"  new_sqlite_classes = ["ChurchDirectory"]   # 새 DO 클래스 = 새 마이그레이션 태그
```

이미 v1 이 배포된 곳에서는 v2 만 새로 적용됩니다. 클래스 이름을 바꾸거나 지울 때는 반드시 새 태그를 추가해야 합니다. 앱의 `ChurchConfig.serverUrl` 은 기존 그대로(`wss://.../ws`)입니다.

## 7. 비용 (쉬운 말, 확인 필요)

**가격과 한도는 제가 확인하지 못한 기억 기준입니다. 아래 계산식으로 배포 전 Cloudflare 요금 페이지의 최신 값을 대입하세요.**

- Durable Object 비용은 (1) **요청 수**, (2) **실행 시간(GB-초)**, (3) 저장소 읽기/쓰기입니다.
- 요청으로 세는 것: 접속 1회(Worker→디렉터리 1건 + 방 1건), 방 알람 1회(0.2초마다 = 접속자가 있는 방은 초당 5건), **들어오는** WebSocket 메시지 20개당 1건, 방→디렉터리 보고(최대 초당 1건/방). 서버가 내보내는 메시지는 요청으로 세지 않는 것으로 알고 있습니다.
- WebSocket 하이버네이션: 연결만 열어 두고 아무 일도 없으면 DO 가 메모리에서 내려가 실행 시간이 과금되지 않습니다. 단 **접속자가 있는 방은 0.2초 알람 때문에 계속 깨어 있어** 사실상 "접속자가 있는 시간 × 128MB" 만큼 실행 시간이 쌓입니다. 자동 응답 핑(`{"t":"ping"}`)은 DO 를 깨우지 않습니다.
- 대략의 규모 예(계산식일 뿐 측정값 아님): 방 34개(2000명), 1시간. 알람 34 × 5 × 3600 ≈ 61만 건. 이동 메시지가 초당 평균 3개/명이면 2000 × 3 × 3600 ÷ 20 ≈ 108만 건. 실행 시간 34 × 0.125GB × 3600초 ≈ 15,300 GB-초. 즉 "2000명이 1시간"은 요청 약 170만 건 + 실행 약 1.5만 GB-초 수준입니다. 알람을 400ms 로 늘리면 알람 요청이 절반이 됩니다(`room.ts` `TICK_MS`, snap 지연 증가).
- 촛불: 켤 때마다 방 저장소 쓰기 2건(촛불 행 + 오늘 카운터)과 방 보고 시 디렉터리 쓰기 1건 이내. `/stats` 는 5초 캐시지만 캐시는 Worker 인스턴스별이라 앱이 자주 부르면 디렉터리 요청이 늘어납니다.
- 대시보드의 **Durable Objects → Metrics**(요청, 실행 시간)와 **Billing** 을 홍보 첫날 직접 지켜보세요. Cloudflare 에는 사용량 알림(Billing → Notifications)을 걸 수 있습니다.

## 8. 용량 가이드 (측정은 `server/church` 에서 직접 한 값만)

- 방 하나가 하는 일: 이동 메시지 처리 + 5Hz 가시 갱신/snap. `--dry`(로직만)에서 방 60명 기준 200ms 창 CPU 는 p95 약 1.5ms, 최악 약 10ms, 평균 점유율 약 0.3%(아래 측정표). 단일 방에 2000명을 몰아넣으면(`--single`) 최악 한 창이 1초를 넘습니다 → **샤딩이 필수**이고 정원 목표 60은 그 여유를 위한 값입니다.
- 한 성당 3000명(50방 × 60)까지는 단계 0, 그 위는 단계 1~2 로 자동 완화되며 입장은 막지 않습니다. 성당 여러 곳에 나뉘면 합계는 성당 수 × 3000.
- 디렉터리는 성당당 DO 하나로 접속 배정(요청 1건)과 방 보고만 처리하므로 초당 수백 건까지는 여유가 있다고 보지만 **실서버에서 직접 확인한 값은 아닙니다**.

## 9. 측정 결과 (이 문서 작성 시 샌드박스에서 실행)
