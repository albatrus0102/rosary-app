# 성당 렌더링 부드러움·스테인드글라스 대량 투입 대비 (작업 D, 2026-11-15)

관련 문서: [PERF.md](PERF.md)(측정 프로토콜·이전 결과), [LOOK_DEV_HANDOFF.md](LOOK_DEV_HANDOFF.md), [GLASS_ALL_CHURCHES_PLAN.md](GLASS_ALL_CHURCHES_PLAN.md), [MILAN_55_PLACEMENT.md](MILAN_55_PLACEMENT.md).
원칙(사용자): 해상도·화질을 낮추지 않는다(동적 해상도는 최후 안전장치), 엔진은 바꾸지 않는다(three.js r149 + Flutter WebView), 텍스처는 앞으로 크게 늘어난다.

**측정 환경의 한계.** 이 문서의 ms 는 헤드리스 Chromium + SwiftShader(CPU 소프트웨어 GL, 4코어, 다른 작업과 함께 돌아 부하 평균 10~12)에서 잰 **상대값**이다. 실제 휴대폰 GPU 의 fps 를 뜻하지 않는다.
기기와 상관없는 값(draw call, 삼각형, 렌더 패스 수, 질감 바이트, 프레임당 렌더 횟수, 할당량)을 주된 근거로 쓴다. 실기기 수치는 설정 '성능 표시' → **30초 벤치**로 받는다(§6).

남은 큰 비용(모바일 GPU 추정, 화질을 건드려야 줄어드는 것 — **이번에 손대지 않음**):
- **MSAA 4× HalfFloat 렌더 타깃**: 360×800 @DPR2 이면 4 샘플 × 8B × 1.15M ≈ 37MB 버퍼 + 해상(blit). 타일 GPU 에서도 WebGL2 의 사용자 프레임버퍼 MSAA 는 메모리 왕복이 생긴다. 줄이려면 MSAA 2×(mid 와 같음) 또는 FXAA/SMAA → 가장자리 품질 변화 → **사용자 결정**.
- **SSAO**(반해상도, 커널 32 + 4×4 블러 + 법선 패스(장면 한 번 더)): 커널 16 으로 줄이면 노이즈가 늘어 블러가 더 필요하다 → 결정 필요.
- 빛줄기 판(창마다 가산 혼합 3장, 양면)·빛 번짐 스프라이트의 투명 겹침: 화면을 크게 덮는 시점(제대를 보며 낮)에서 오버드로가 크다. 장수를 줄이면 모양이 바뀐다.
- 물리 재질(MeshPhysical, clearcoat) + PMREM + PCF soft 그림자: 화소당 ALU 가 크다. 베이크(라이트맵)로 바꾸면 크게 줄지만 성당이 코드로 생성되어 앱 안 베이크 단계가 필요하다(§7 보류).

### 3.2 예산표(창 질감)

1k = 긴 변 1024px. 세로창(약 0.5:1) RGBA8 + 밉맵 ≈ 2.7MB, 원형 1:1 ≈ 5.3MB, 2k 는 ×4. 창 판은 조명·그림자·SSAO 밖이라 화소 비용은 질감 1번 표본뿐이다.

| 방식 | 창 55장 GPU 메모리 | 창 64장 | draw call(창) | 입장 때 디코드·업로드 | APK(창 55장) |
|---|---|---|---|---|---|
| 예전: 창 id 마다 1k 상주 | 약 150MB(원형 많으면 290MB) | 약 175~340MB | 창 id 수(55) | 55장 전부(입장 직후 한꺼번에) | 1k webp 평균 210KB → 약 11.5MB(+base64 팩 오버헤드는 zip 이 대부분 되돌림) |
| 예전 + 2k | 600MB~1.2GB(불가) | — | 55 | 55 × 4배 | 약 40MB |
| **스트리밍 high**(먼 창 256px 아틀라스 + 가까운 창 ≤8장, ≤64MB) | 아틀라스 18.7MB + ≤64MB = **≤ 83MB** | 21MB + 64 = ≤ 85MB | **1 + ≤8** | 먼 층 팩 1개(55장 ≈ 1.4MB) + 걷는 대로 1장씩 | 1k 11.5MB + 먼 층 1.4MB |
| 스트리밍 mid(≤6장, ≤40MB) | 18.7 + 40 = ≤ 59MB | ≤ 61MB | 1 + ≤6 | 같음 | 같음 |
| 스트리밍 low(128px 아틀라스, ≤4장, ≤24MB) | 4.7 + 24 = ≤ 29MB | ≤ 30MB | 1 + ≤4 | 같음 | 같음 |
| (선택) KTX2 ETC1S → ETC2/ASTC(1B/화소) | 위 값의 약 1/4(가까운 창 8장 ≈ 6~11MB) | — | 같음 | 디코드 대신 워커 트랜스코드(1k 11~70ms, 업로드 < 1ms) | ETC1S 1k ≈ 170~200KB(webp 와 비슷), UASTC ≈ 700KB. 트랜스코더 +0.6MB |

전체 GPU 예산(목표 256MiB 이내) 안의 몫: 장면 사진·캔버스 질감 약 65MB(성 베드로) + 렌더 타깃(360×800@2, high) 약 70MB + 창 ≤ 83MB → 약 220MB. 폴더블 대화면(픽셀 2.5배)은 렌더 타깃이 커져 넘칠 수 있다 → §8 질문.

### 3.3 구조

- **먼 층(far)**: `gpack_far_<성당>.js` 하나에 창마다 긴 변 256px webp(`build_glassfar.mjs`). 입장 때 한 번 읽어 캔버스 아틀라스(칸 256px, 비율 그대로, 2px 여백)로 모아 **질감 1장·메시 1개·draw call 1**. 올린 뒤 캔버스는 1×1 로 줄여 CPU 메모리를 놓는다. low 는 칸 128px.
- **가까운 층(near)**: 창 id 마다 `gpack_<id>_1k.js`. 0.25초마다 `ChurchGlassStream.plan()`:
  - 점수 = 정면에서 볼 때 화면 긴 변 px = 창 긴 변 × focal / 거리(focal = 렌더 높이 px / (2·tan(fov/2)), 실제 화소 비율 반영).
  - 들어가기: 점수 > 칸 px × 0.9, 남기: × 0.6(히스테리시스). 이미 있는 것은 1.15배 우대.
  - **고르기는 시야와 무관**(고개만 돌리면 읽기·해제 0 — 시험으로 고정). 시야는 읽는 순서만 앞당긴다.
  - 상한(high 8장/64MB · mid 6/40 · low 4/24)을 넘으면 점수 낮고 오래 안 쓴 것부터 해제(LRU). 상한 안에서는 원하지 않아도 남겨 둔다(되돌아올 때 다시 읽지 않게).
- **디코드·업로드**: data URI → `fetch` → Blob → `createImageBitmap`(flipY·비곱셈 알파·색공간 변환 없음 = three 기본과 같은 화소)로 **메인 스레드 밖**. 동시에 1장. 업로드는 `update()` 에서 **프레임당 1장**(`initTexture`, 밉맵 GPU 생성), 올린 즉시 ImageBitmap 을 닫고 팩 문자열·`<script>` 를 놓는다. `createImageBitmap` 이 없으면 `<img>.decode()`.
- **교차 페이드**: 가까운 판(renderOrder 5.6, polygonOffset)이 먼 판 위에 0.25초 페이드, 끝나면 먼 층의 그 자리 정점을 접는다(같은 화소를 두 번 칠하지 않게). 해제할 때는 먼 판을 먼저 되살린다.
- **해제**: 성당을 바꾸면 먼 층·가까운 층 질감·메시·재질 모두 dispose(예전과 같음).
- **같은 재질·셰이더**: 먼 층·가까운 층 모두 감상 모드와 같은 유리 셰이더(프로그램 1개). 창이 늘어도 셰이더 수는 그대로.
- **창 지오메트리**: 판은 자리마다 사각형 2삼각형. 창틀·트레이서리는 빌더 메시(정적 배치)에 그대로 두고 판은 그 안쪽 1.2cm 앞에 놓는다. 비율은 사진 비율 그대로(개구부를 맞춘다), 원형·타원은 사진 알파로 자른다(사용자 자료의 '개구부별 마스크'는 같은 알파 경로로 넣으면 된다).
- **측랑 벽을 창으로 바꿀 때(사용자 다음 작업)**: 키트 벽(`ctx.wall`)은 지연 생성이라 같은 벽 위에 `ctx.window({x, y, z, face, w, h, top, photo: ctx.glassPhoto(slot, i)})` 를 베이마다 부르면 `_prepare` 가 구멍을 데이터로 뚫고(matchWindows) 창틀을 붙인다. 손으로 지은 벽은 개구부를 뚫고 `ctx.glassSlot({photo, x, y, z, face, w, h})` 로 자리를 알린다. 즉 측랑 벽은 '베이 = 창 자리' 데이터 목록으로 다룰 수 있다(대응표 `glass_placements.js` 의 `repeat` 슬롯). 자리 수가 늘어도 위 구조라 draw call·셰이더는 늘지 않고, 질감은 상한으로 묶인다. 빛줄기(`S.beams`)는 창마다 가산 판 3장이라 창을 많이 늘리면 오버드로가 늘어난다 → 측랑 창은 빛줄기를 베이 2~3개에 하나만 두는 것을 권장.
- **팩 크기·파싱**: 1k 팩 1개 = base64 약 270KB 문자열 1개(파싱 수 ms). 한 번에 하나만 읽고 바로 놓으므로 JS 힙에 큰 문자열이 쌓이지 않는다. 55장을 한 파일로 묶지 않는다(입장 때 15MB 파싱 금지).

### 3.4 KTX2/Basis(GPU 압축) — file:// WebView 에서 가능 여부: **가능(검증)**

헤드리스 Chromium file:// 페이지(WebView 와 같은 불투명 출처, `fetch(file://)` 차단)에서 확인:
- `fetch('basis_pack.js')`(file://) → 차단(예상대로). `fetch(blob:)`·`fetch(data:)` → 됨. `new Worker(blob: URL)` → 됨. `createImageBitmap(Blob)` → 됨.
- r149 `KTX2Loader` 를 클래식 번들로 묶고(55KB), 트랜스코더(js 62KB + wasm 500KB)를 base64 팩에 넣어 `LoadingManager.setURLModifier` 로 blob URL 을 넘기면 정상 동작. r149 에는 `parse()` 가 없어 `_createTexture(buffer)` 를 쓴다.
- 결과(1k 창 3장): ETC1S 174~201KB(webp 182KB 와 비슷), UASTC+zstd 696~749KB. 트랜스코드 11~70ms(첫 장 169ms, wasm 초기화), 업로드 0.2~0.7ms. 데스크톱에서는 BC7/ASTC 로 풀렸다. **가로·세로가 4의 배수가 아니면(534px) BC7 업로드가 INVALID_OPERATION** → 변환 파이프라인에서 4의 배수(가능하면 2의 거듭제곱)로 맞춰야 한다.
- 결론: 구조상 쓸 수 있다. 이번에는 **번들에 넣지 않았다**(APK +약 0.6MB, 화질 검증(ETC1S 블록 노이즈) 필요, 사용자 지시대로 별도 파이프라인에서 검증). 스트리밍 코드는 디코더만 바꾸면 되도록 나눠 두었다(`decodeUri` → KTX2 이면 `CompressedTexture`).

## 7. WebView 구조의 근본 한계(정직하게)

- **합성 경로**: Flutter 의 WebView 는 TLHC(질감 레이어) 방식이라 WebView 가 그린 프레임을 Flutter 가 한 번 더 합성한다(전체 화면 복사 1회 + vsync 정렬 지연 최대 1프레임). 최적화로 없앨 수 없다. 대신 같은 화면에 Flutter 위젯 애니메이션이 많으면 Flutter 쪽 래스터 비용이 더해진다.
- **WebGL 드라이버 오버헤드**: draw call 하나가 JS → 명령 버퍼 → GPU 프로세스(ANGLE/GLES)로 간다. 네이티브 엔진보다 호출당 비용이 몇 배 크다. 그래서 draw call 을 줄이는 구조(병합·아틀라스·패스 합치기)가 가장 중요했다.
- **스레드**: 렌더·게임 로직·디코드 요청이 모두 WebView 메인 스레드 하나다. 디코드는 `createImageBitmap`·워커로 뺄 수 있지만 three.js 렌더 호출 자체는 나눌 수 없다(OffscreenCanvas 워커 렌더는 Android WebView 에서 가능하나 three.js 구조·입력 처리 전체 이전이 필요 → 보류).
- **GPU 압축 텍스처**: 가능하다(§3.4). 다만 트랜스코딩(wasm)이 필요해 네이티브 엔진(빌드 때 ASTC/ETC2 로 굽기)보다 로딩이 한 단계 많다.
- **메모리**: WebView 렌더 프로세스는 앱과 별도이며 GPU 메모리 한도가 Chrome 정책에 묶인다. 대화면·고해상도에서 렌더 타깃이 커지면 상한에 먼저 걸린다.
- 이 한계들 때문에 같은 장면을 Unity 네이티브로 그리면 CPU 쪽(드로콜·스크립트) 여유는 분명 더 크다. GPU 화소 비용(후처리·MSAA·투명 겹침)은 엔진이 바뀌어도 같은 화질이면 비슷하다.

기준 기기: 사용자의 중급 Android 폰. 조건: 밀라노 + '창 55 스트레스' 켬, 화질 high(자동), 기기 기본 해상도.

| 판정 | 30초 벤치 결과 | 해석 |
|---|---|---|
| **three.js 유지** | 평균 ≥ 50fps 그리고 1% low ≥ 30fps 그리고 100ms 넘는 프레임 0~1개, 30분 사용 뒤 같은 벤치가 10% 안쪽 | 남은 일은 콘텐츠·화질 |
