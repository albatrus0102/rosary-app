### 1.3 창은 어떻게 만들어져 있나 (메시 구조)

- `ch_milan.js` 의 창은 키트 창(`ctx.window`)이 아니라 빌더 안의 `windowPanel()` / `windowPanelPoly()` 가 손으로 짓는다: 벽 판에 **진짜 구멍**을 내고(`starRing`), 안쪽 스플레이, 납틀 뒷판, 유리 칸(색 면), 문설주·가로대(돌 상자), 아치 몰딩, 빛줄기를 만든다.
- **창마다 따로 된 Mesh·이름·슬롯은 없다.** 유리 칸은 전부 `glass` 배치(Mesh 이름 `glass`, renderOrder 1) + `glassRefl`(반사 막, renderOrder 4) 한 덩어리로 합쳐지고, 벽·창살은 `surf_stone_grey`/`solid` 배치에 들어간다. 지시서가 요구하는 "실제 씬 mesh ID"에 해당하는 것이 지금은 없다 → 이 문서는 조회 스크립트가 붙인 **개구부 key**(`aisleS_b1` 등)를 식별자로 쓴다. 구현 뒤에는 사진 판 Mesh 의 `userData`(지금 `glassPlace = <창 id>`)에 DEV id 와 개구부 key 를 싣는 것을 제안한다.
- 사진을 거는 기존 경로(G-29): 빌더가 `ctx.glassSlot({photo, x, y, z, face, w, h})` 로 자리를 알리면 `world.glassSlots()` → `glass_place.js` 가 절차적 유리 1.2cm 앞에 사진 판을 깔고, 성당을 바꾸면 해제한다. 밀라노의 슬롯은 지금 `apse_center_lower` 하나뿐이다.
- `S_.windows`(키트 창 목록)는 밀라노에서 비어 있다 → 14처 판 자리 유도·감상 모드의 '가장 가까운 창' 같은 일반 로직은 밀라노 창을 모른다.

## 2. 실제 평면(P 번호) ↔ 모델, 55행 분류

### 2.1 대응 원칙

- 남측랑 P01~P08 = `aisleS_b1…b8`(입구에서 제대 쪽으로), 북측랑 **P39 = `aisleN_b1`(입구 쪽 첫 창) … P32 = `aisleN_b8`**. 지시서의 글("입구에서 제대 방향 n번째")과 그대로 맞는다.
- 후진 P19(남)·P20(중앙)·P21(북) = `apse_south`·`apse_center`·`apse_north`.
- **익랑 안의 순서는 추정이다.** 공개 도면 그림은 이 작업 환경에서 열지 못했다(위키미디어 공용이 429 를 돌려주었고 그 뒤 재시도는 하지 않았다). 지시서의 글만으로 정했다: "P09·P10 = 남익랑 서쪽으로 접근하는 벽, P11~13 = 끝 경당(측면·끝 중앙·측면), P14·P15 = 동쪽 복귀 구간" → 모델에서 벽을 따라 도는 순서 `trWestS → trEndS_west → (경당) → trEndS_east → trEastS`. 북익랑은 거울: P25 = `trEastN`, P26 = `trEndN_east`, (경당 P27~29), P30 = `trEndN_west`, P31 = `trWestN`. 도면을 확인하면 표의 key 만 바꾸면 된다(스크립트의 `PLAN` 표).
- 경당 6창(P11~13, P27~29)과 경당 상부(V12bis)는 **건축 자체가 없다**. 끝 벽 가운데 큰 창(`trEndS_center`, `trEndN_center`)이 같은 축 위의 유일한 자리지만 "창 3개 → 창 1개"이므로 임의 배정하지 않고 (c) 로 둔다. P12·P28 을 그 큰 창에 **대역**으로 걸지는 사용자가 정한다(질문 3).
- 회랑 P16~18·P22~24: 모델의 맹벽이 한쪽에 정확히 3구간(§1.5 위 세 줄) 있지만, 실제로 그 창들이 어느 벽인지 확인하지 못했고(주제도 5개가 미확인) 그 바깥은 성구실이다 → (b), 임의로 뚫지 않는다.

### 2.2 정문 안쪽 하단의 방향 충돌 (P40 ↔ V40) — 우리 좌표로

- 도면(정문 아래·제대 위로 읽음)의 하단 번호는 왼쪽부터 P40, P41, P45, P42, P43. 도면의 왼쪽 = 제대를 볼 때 왼쪽 = 북 = **−x**. → P40 은 가장 북쪽(−x 끝), P43 은 가장 남쪽(+x 끝), P45 가 가운데(x = 0).
- 공식 V40 설명은 "성당 안에서 정문을 바라볼 때 맨 왼쪽". 정문(+z)을 보면 왼손 쪽은 **+x(남)** 이다. → V40 은 +x 끝.
- 즉 **P40 = −x 끝, V40 = +x 끝으로 서로 반대**다. DEV-041(V40)을 `P40` 자리에 강제하지 않는다. DEV-042(P42/V42)도 같은 이유로 좌우가 확정되지 않는다(P42 는 도면상 +x 안쪽 칸, V 번호가 안쪽에서 본 왼쪽부터라면 V42 는 −x 쪽). 가운데 V45/P45(DEV-045)만 좌우 문제가 없다.
- 결론: 하단 5창은 (가) 개구부가 없고 (나) 좌우가 미확정이다. 개구부를 만들더라도 041~044 는 좌우가 확인될 때까지 QA Gallery 에 둔다.

### 3.3 마스크·분할 제안 (늘리지 않기)

기존 G-29 규칙은 "개구부를 사진 비율에 맞춰 다시 짓는다"였다. 임시 시안은 곧 바뀔 그림이므로 **건축을 시안에 맞추지 않는다.** 대신 판 단위로 맞춘다.

1. **기본 = contain + 위 맞춤**: 판은 텍스처 비율 그대로(왜곡 0), 폭은 개구부 폭 이하, 꼭대기를 개구부 꼭대기에 맞춘다(그림의 첨두와 개구부의 첨두가 포개진다). 남는 곳(양옆 띠·아래)은 절차적 유리 대신 **어두운 납틀색**으로 덮어 "임시 그림은 여기까지"가 분명히 보이게 한다.
2. **개구부 마스크**: 판은 사각형이고 셰이더에서 개구부 윤곽 밖을 버린다. 윤곽은 측정값 세 개로 정해진다(반폭 a, 기공 높이, 아치 높이 `rise`): 기공 위에서는 `(|u| + Rr − a)² + (y − spring)² ≤ Rr²`, `Rr = (a² + rise²) / 2a`(`ch_milan.js` 의 `pf()` 와 같은 식). 텍스처 알파와 곱한다. 판 모서리는 스플레이 뒤라 정면·사선 모두에서 가려진다(기존 사진 판과 같은 깊이).
3. **cover(자르기)는 창살이 어긋나지 않는 곳만**: 측랑 7·8칸처럼 개구부가 낮은 곳은 폭을 맞추고 아래를 잘라도 된다(랜싯 그림 아래 31~35% 가 잘린다). 늘리기는 하지 않는다.
4. **분할**: 후진 3창과 익랑 끝 큰 창은 모델의 문설주로 3~4랜싯으로 나뉘어 있다. 랜싯 1장을 랜싯마다 반복해 채우는 방법은 가능하지만(랜싯 폭 1.17~1.47m, 비율 0.11~0.14 → 랜싯 시안을 cover 로) **같은 그림이 3~4번 반복**된다. 임시로라도 "한 창 = 한 그림"이 아니게 되므로 기본안에서 제외하고 선택 사항으로 둔다.
5. UV: u 는 실내에서 볼 때 왼→오, v 는 아래→위(three 기본 `flipY`). 판 생성은 `glass_place.js buildMesh` 규약을 그대로 쓰면 좌우가 뒤집히지 않는다(남측 창: u 가 +z 쪽 = 실내에서 본 오른쪽). 구현 때 글자가 있는 시험 텍스처로 한 번 확인한다.

## 4. 구현 선택지와 추천 (사용자 결정용)

### 4.1 공통 전제

- 임시 시안은 **진본 대응표(`glass_placements.js`)에 넣지 않는다.** 그 표는 "카탈로그의 `authentic` 창만"이라는 규칙을 `glass_place.test.mjs` 가 고정하고 있고, 창 정보 시트·'이 창:' 칩으로 이어진다. 시안은 별도의 개발 전용 표(`dev` 표시, 카탈로그에 없음)로 다룬다.
- 성당 출입 시 해제는 기존 `glass_place.clear()`(판·질감 dispose, `stats.created/disposed`)를 그대로 쓰거나 같은 계약을 따른다. 시험: 밀라노 → 다른 성당 → 밀라노를 돌아 `disposed == created`, 상주 질감 수 0.
- 성능 담당이 스테인드글라스 로딩·스트리밍을 새로 설계 중이므로 **배치는 데이터로만 정의**한다: `{dev_id, opening_key, x, y, z, nx, nz, w, h, mask:{a, spring, apex}, fit:'contain-top', dev:true}`. 좌표는 이 문서의 표(= `milan_openings.mjs --json --match`)에서 나온다. 로더가 무엇이 되든 이 표를 읽으면 된다.
- 빌더를 고쳐도 된다면 `windowPanel()` 이 개구부마다 `key` 와 윤곽을 등록하게 하는 것이 가장 깔끔하다(지금은 창별 식별자가 없다). 그 전에는 조회 스크립트의 측정값을 표로 쓰고, 노드 시험이 "표의 좌표 = 빌더를 돌려 잰 값"을 고정한다.

릴리스에 **들어가지도, 보이지도** 않게 세 겹으로 막는다.

1. **포장(파일이 APK 에 없다)**

2. **컴파일 플래그(코드 길이 막혀 있다)**

3. **실행 때 표시(보이면 임시라고 쓴다)**

```
node tools/church_web/milan_openings.mjs            # 개구부 67개(구역별, world 좌표·법선·크기)
node tools/church_web/milan_openings.mjs --match    # 55행 분류(a/b/c/d), contain 판 크기·텍셀, 중복 anchor 검사
node tools/church_web/milan_openings.mjs --json --match   # 구현용 JSON
node tools/church_web/milan_openings.mjs --md       # 이 문서의 표(§1.4, §2.4)
```

- 스크립트는 `church_harness.mjs` 와 같은 방식(가짜 canvas, vm)으로 `ch_milan.js` 를 그대로 돌리고, 납틀 뒷판(`solid.addTris`, 색 0x2c241f)과 유리 칸(`glass.addTris`) 호출을 가로채 개구부를 잰다. 씬 코드는 고치지 않는다. `ch_milan.js` 의 창 치수가 바뀌면 다시 돌리면 된다(이 문서의 표도 `--md` 로 갱신).
- 캡처(`art/glass_milan55/shots/e1_*.jpg`, 640px): `test.html?church=milan&quality=mid&hour=11` 을 헤드리스 크롬(swiftshader)으로 열고 카메라를 직접 놓아 찍었다. 남측랑 정면(4.6, 3.2, 19.1 → +x), 북측랑 제단 칸, 남익랑 끝 벽, 후진 회랑, 회랑 남쪽 맹벽, 정문 안쪽. 작업 트리에서 다른 작업이 진행 중이라 벽 색·조명은 찍은 시점마다 다르다(창 배치와는 무관).

## 7. 한계 (정직하게)

- 공개 도면(Dell'Orto)·CVMA 도면 **그림을 직접 보지 못했다.** P 번호의 위치는 지시서의 글 설명에 의존한다. 측랑(16)·후진(3)은 글이 분명하지만 익랑 8개는 벽을 도는 순서로 추정했다.
- 모델의 익랑·후진·정문 안쪽은 실제 건축을 단순화한 것이다(끝 경당 없음, 후진 창 크기 실제 4.51×10.70m 환산보다 작음, 정문 문 위치가 기둥줄). 이 문서는 "지금 모델에 있는 것"을 기준으로 분류했다.
- 텍스처 55장은 실제 작품의 도상·배치가 아니다. 이 문서의 P/V ↔ DEV 대응은 개발 시험용 번호 맞춤이다. 실제 복원 텍스처로 바꾸기 전에 원작·사진·문화유산 권리를 따로 확인해야 한다(README_KO.md).
- 화질 판단(§3.4)은 계산값이다. 실제 판을 걸어 찍은 화면은 구현 단계에서 확인한다.
